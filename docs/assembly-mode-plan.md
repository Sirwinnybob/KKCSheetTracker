# Assembly Mode — Full Implementation Plan

## Context

KKCSheetTracker has two work modes: CNC (sheet-by-sheet cutting progress) and Hardwoods (row-by-row cut list progress). Assembly workers need a third, read-only mode that lets them:

1. Monitor CNC and Hardwoods production progress across jobs from a single dashboard
2. View Plans & Elevations and Assembly Sheets side-by-side in a synchronized viewer
3. Jump both PDFs simultaneously to the sheet(s) containing any cabinet number
4. Pull up a parts checklist per cabinet showing what CNC cut and what Hardwoods cut

The infrastructure for cabinet→page mapping already exists (`cabinet_sheet_index.json` generated by `cabinet_sheet_indexer.py`). Phase 1 makes parsing rock-solid via structured text markers before building the app features on top.

## Assembly Sheet Parts Index ✅ COMPLETE

### Context

Assembly workers look at the assembly sheet for a cabinet and want to know, for each part listed, whether it has already been cut — by CNC (plywood/sheet goods) or by Hardwoods (face frame rails/stiles, nailers). The assembly sheet is the master bill-of-materials for a cabinet. Parts live under pipe-delimited section headers (`| Frame |`, `| Panel Stock |`, `| Hardware |`, etc.). Each part is exactly **5 consecutive text lines**: qty, width, length, description, material.

### What was built

**Python (`cabinet_sheet_indexer.py`):**
- `_extract_section_name()` — identifies `| Frame |`-style headers, filters CV metadata noise
- `_is_part_description()` — requires a letter; filters bare-number diagram data at page bottom
- `_parse_assembly_parts_for_page()` — 5-line group parser, emits `{qty, width, length, description, material, sectionType, isPurchased}`
- Integrated into both `_try_parse_with_markers` and `_parse_assembly_pdf` fallback paths
- 43 tests total (including 5 new), all passing

**Android models (`Models.kt`):**
- `AssemblySheetPart` — parsed from assembly sheet PDF
- `CabinetPageDetail.parts: List<AssemblySheetPart>` — Gson picks up automatically
- `AssemblyBomEntry(part, cncPart?, hardwoodRow?)` with `isTracked` property
- `AssemblyCabinetParts.bom: List<AssemblyBomEntry>` added alongside legacy `cncParts`/`hardwoodRows`

**Android logic (`AssemblyStateStore.kt`):**
- `deriveBomForCabinet()` — looks up assembly index pages, matches parts by description (case-insensitive trim) to CNC parts by `partName` and hardwood rows by `description`

**Android UI (`AssemblyViewerScreen.kt`):**
- `BomPartsContent` — groups by `sectionType`, renders `BomPartRow` per entry
- `BomPartRow` — status icon + qty × description + dimensions chip (CNC/HW/Purchased/Not Indexed)
- Falls back to `LegacyPartsContent` when BOM is empty

## Phase 3D — 3D Viewer Integration (WebView + NanoHTTPD)

### Context

Assembly workers use the standalone **AssimpAndroid** app to view 3D room models exported by Cabinet Vision. The models live at `<JOB>/3D/<ROOM_NAME>/3d.dae`. Workers want a mini 3D viewer directly in one of the side-by-side panes of `AssemblyViewerScreen`. A "Full Screen" button launches AssimpAndroid via Intent for full controls.

### Architecture Decision: WebView + NanoHTTPD (not C++/JNI)

The existing **KKC_Portal** web app uses a Three.js viewer (`viewer.html`) that already handles orbit/zoom/pan, post-processing, and LOD. Rather than rewriting C++/JNI from scratch, we:

1. **Strip** KKC_Portal's viewer to view-only (remove texture panel, showroom, camera capture)
2. **Bundle** the stripped viewer HTML/JS/CSS + Three.js module into the APK as assets
3. **Run NanoHTTPD** locally inside the app — serves assets from APK, serves `.glb` files from local job folder
4. **Convert** `.dae → .glb` in Ready Jobs Watcher so GLB files are available offline
5. **WebView** loads `http://127.0.0.1:PORT/viewer.html?job=FOLDER&room=ROOM`

**Full-screen button still launches AssimpAndroid via Intent** (unchanged).

This approach is fully offline — no network server required, everything runs on the tablet.

### Feature Comparison

| Feature | This plan (WebView) | AssimpAndroid (full-screen) |
|---------|--------------------|-----------------------------|
| Orbit / zoom / pan | ✅ Three.js OrbitControls | ✅ |
| Post-processing | ✅ KKC custom shader | ✅ |
| Edge line overlay | ❌ | ✅ |
| Part hiding + undo/redo | ❌ | ✅ |
| LOD (high/med/low) | ✅ | ❌ |
| Texture swapping | ❌ (stripped) | ❌ |
| Offline | ✅ (NanoHTTPD) | ✅ |
| NDK / C++ required | ❌ | ✅ (already built) |
- Lighting toggle — unlit ↔ Gouraud shading
- MSAA — 4x → 2x → none fallback chain
- Cabinet label display from node name parsing
- Frustum culling via bounding spheres

### Architecture Decision

AssimpAndroid's rendering is ~3,000 lines of C++ (OpenGL ES 2 + Assimp library), called via JNI. SceneView/Filament doesn't support edge line rendering, ray-triangle part picking, per-node hiding, or custom post-processing shaders. **Approach:** copy C++ source into KKCSheetTracker, strip all AR code, adapt JNI bridge for KKCSheetTracker's package name, wrap `GLSurfaceView` in Compose `AndroidView`.

**Assimp prebuilt:** `C:\Scripts\Assimp\assimp\build_android_arm64-v8a\bin\libassimp.so`
**Target ABI:** `arm64-v8a` only (matches AssimpAndroid's build)

### Phase 3D-E — DAE Sanitization

Kotlin, not Python — operates on a copy in app internal storage:

```kotlin
fun sanitizeDaeToInternalStorage(source: File, internalDir: File): File {
    val dest = File(internalDir, source.name)
    source.copyTo(dest, overwrite = true)
    File(source.parentFile, "images").takeIf { it.exists() }
        ?.copyRecursively(File(internalDir, "images"), overwrite = true)
    val text = dest.readText()
    val cleaned = text.replace(Regex("(?s)<h>.*?</h>"), "")
    if (cleaned != text) dest.writeText(cleaned)
    return dest
}
```
